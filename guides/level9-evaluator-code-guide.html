Evaluator 실물 코드 - 사용 가이드

발표자료가 설명하는 채점 모델(100점 채점표 · 거부권 · 5축 루브릭 · 재작업 루프)을 실제로 돌아가는 Java·Python 코드로 옮긴 것이다. 슬라이드의 숫자와 코드의 숫자가 같고, 테스트가 그 일치를 검증한다. 빌드 도구·테스트 프레임워크·API 키가 필요 없다.

저장소
claude-code-expert/carve-harness
경로
docs/evaluator/deck-example/
언어
Java (JDK 11+) · Python 3
기존 예시와의 관계

저장소에는 이미 java-example · python-example 이 있다. 그것들은 LLM-Judge 한 층을 보여주는 좋은 샘플이지만 채점이 1/3/5점이라, 발표자료의 100점 만점 · 90점 합격과 숫자가 어긋난다. 이 deck-example 은 그 위에 채점표 전체를 보여주며, 기존 예시를 대체하지 않고 나란히 놓인다.

PART 2슬라이드 ↔ 코드 대응표

발표 중 "이 부분이 코드로는 여기입니다"라고 짚을 수 있게 1:1로 맞췄다.

슬라이드개념구현

74~75쿠폰 API 워크스루97/70/92/100 → 97/96/97/100 재현

PART 3설계에서 눈여겨볼 세 가지

1. 거부권은 한 줄이다

총점이 합격선을 넘어도 안전 항목이 0이면 실패다. "거의 다 됐다"를 산술적으로 없애는 자리다.

boolean veto = items.get("g1_build") == 0
            || items.get("g2_test")  == 0
            || items.get("g3_safety") == 0;

verdict = veto ? FAIL : (total / max >= 0.9 ? PASS : FAIL);

테스트로 고정: 안전 0점 → 총점 85 → FAIL. lint 0점 → 총점 90 → PASS(거부권 아님).

2. test 축이 거짓 완료를 막는다

test 는 실행 출력에서만 채워진다. 테스트를 돌리지 않으면 0점이고, 나머지 네 축을 만점 받아도 합이 75 라 임계 95를 넘을 수 없다. 

exists 25 + match 25 + test  0 + contract 15 + no_regress 10 = 75   < 95

게이트에 "테스트를 돌렸는지 확인하라"는 규칙을 따로 넣지 않아도 배점 자체가 막는다. 규칙을 늘리는 대신 구조로 강제하는 예다.

3. 못 잰 것과 나쁜 것은 다르다

커버리지 리포트가 없을 때 0점을 주면 억울한 감점이 되고, 만점을 주면 조용한 통과가 된다. 그래서 분모에서 뺀다. skipped 목록에 남으므로 무엇을 못 쟀는지도 드러난다. 

전 항목 측정  → 100/100  PASS
커버리지 없음 →  95/95   PASS     (coverage 는 skipped)
아무것도 없음 →   0/0    UNABLE   (PASS 아님 - fail-closed)

PART 4워크스루가 재현되는지 보는 법

발표자료 74~75p 의 점수표가 코드에서 그대로 나온다. 테스트가 그 숫자를 단언으로 고정하고 있어, 구현이 바뀌면 테스트가 깨진다.

채점 항목1회차2회차재작업 지시
coupon-applies97 ✓97 유지-
coupon-no-reuse70 ✗96 ✓중복 사용 테스트가 아예 없음 → test 축 0점
coupon-expiry92 ✗97 ✓만료 경계 미검증 → match 축 미달
coupon-response-shape100 ✓100 유지-

1회차에서 게이트는 BLOCKED 이고 재작업 대상은 미달 2개뿐이다. 통과한 항목은 손대지 않는다 - 전체 재생성이 아니라 미달만 고치니 빠르고, 이미 좋은 것을 망치지 않는다.

92점도 차단이다

coupon-expiry 가 92점으로 막히는 것이 이 예제의 핵심 장면이다. "거의 됐다"는 판정에 없다. 합격선 아래는 전부 같은 미달이다.

채점기 버그 재현 - 87p

같은 답을 두고 채점기만 바꿨을 때 통과율이 어떻게 변하는지 보여준다. "채점기부터 의심하라"가 왜 순서 1번인지가 여기서 드러난다. 

정답 96.12 에 대한 응답들:  "96.120"  " 96.12"  "96.12"  "100.0"

문자열 비교 채점기   1/4 통과      ← 에이전트가 틀린 것처럼 보인다
숫자 비교 채점기     4/4 통과      ← 답은 처음부터 맞았다

PART 5자기 프로젝트에 옮기는 절차

01골든셋을 자기 도메인으로 바꾼다

goldenset/coupon-api.json 을 복사해 항목을 자기 것으로 교체한다. 항목마다 claim(무엇을 했다고 주장하는가)과 acceptance(무엇이 충족의 증거인가)를 쓴다.

케이스는 사람이 검수한다. 에이전트가 혼자 만들면 자기가 이미 통과하는 것만 담아 지표가 무의미해진다.

02측정 어댑터에 자기 툴체인을 연결한다

실제로 명령을 돌리고 종료 코드를 넘긴다. 이 부분만 바꾸면 언어·스택과 무관하게 동작한다.

from_exit_code(run("./gradlew test"), "gradlew test")     # G2
from_exit_code(run("./gradlew spotlessCheck"), "spotless") # lint
from_coverage(parse_jacoco(), minimum=0.8)                 # coverage
03못 돌리는 항목은 null 을 넘긴다

툴체인이 없거나 리포트가 없으면 0점이 아니라 null 이다. 그래야 skipped 로 가고 분모에서 빠진다. 여기를 0점으로 처리하면 팀이 채점을 불신하게 되고, 만점으로 처리하면 조용한 통과가 생긴다.

04루프를 돈다

loopStatus() 가 RELEASED 를 돌려줄 때까지 미달 항목만 재작업한다. 항목당 재시도 상한(3회)을 두고, 넘으면 사람에게 에스컬레이션한다.

S1 분해   → S2 구현 → S3 채점 → S4 미달만 되먹임 → S2
                                 ↓ 전 항목 통과
                              S5 종료
05CI에 건다

두 스크립트 모두 실패 시 exit 1 이므로 워크플로 스텝에 그대로 넣으면 된다. 채점기 자체가 깨졌을 때 조용히 통과하지 않는 것이 요점이다.
